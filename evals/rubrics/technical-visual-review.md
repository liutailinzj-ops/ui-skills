# 技术视觉验收

本检查只用于 Skill 开发、回归和稳定性评估，不属于 UI 日常生产流程，也不得被生产 Skill 自动展示给 UI 或客户。

## 使用顺序

1. 在独立测试文件或 Sandbox 页面运行案例。
2. 获取参考来源、目标主题证据、Visual Direction Contract、代表性模块和最终 Desktop/Mobile 截图。
3. 先进行本视觉验收，再检查 Rxx、组件、Auto Layout、Text Style 和节点结构。
4. 任一视觉阻断项命中时，案例直接失败；技术结构通过不能覆盖视觉失败。

## 一眼否决项

- 大面积黑色或单色矩形被当作最终图片与模块设计。
- 与上一版或其他无关案例使用相同的固定配色、卡片、长页节奏和构图语法，只替换文案与模块名称。
- 参考网站只被转换成内容清单，没有转换其视觉层级、媒体关系、连接结构和响应式逻辑。
- 主题映射只存在于报告，Figma 画布没有按主题模块的真实组合方式呈现。
- 交给 UI 后仍需重新决定首屏、图片构图、信息层级或大部分模块布局。
- 页面只能被称为线框、结构稿或合规报告，不能被视为 UI 初稿。
- 因客户素材不足而用同一套抽象几何、空图片框或重复图片代替不同产品、配置、功能或场景；文字不同但视觉没有表达差异。
- 客户预览中出现 QA、Rxx、主题映射、实现标签或替换说明。
- Desktop/Mobile 使用不同文案、不同 Section 身份或无依据的独立构图，只保留了相似配色。
- 同一对齐组左右边界误差超过 1px，或出现没有主题/基础规范依据的容器宽度变化。
- 普通子节点超出开启裁切的父节点，导致内容、链接、卡片或控制项被隐藏。

## 通过条件

- 第一眼能够识别项目的品牌气质、产品类型和主要视觉方向。
- 代表性模块与完整页面继承同一套项目专属视觉语言。
- 真实或临时图片具有明确的主体、比例、裁切、密度和构图作用。
- 缺少客户素材时仍具备可评审的临时品牌与视觉资产；不同产品、配置、功能或场景在视觉上可区分。
- 指定参考的内容与布局逻辑被视觉化转换，而不是仅做语义覆盖。
- 主题建站结果看起来像目标主题能够实现的完整设计，而不是与主题无关的通用 Figma 模块。
- Desktop 和 Mobile 是同一响应式 Section 系统的可用断点状态，内容、组件和视觉身份连续。
- 同组边界、父子包含、内容一致性与显式溢出合同通过节点级检查。
- UI 可以在保留主要布局的前提下调整素材、文案、颜色、间距和局部创意细节。

## 结果

- `通过`：视觉交付物达到可进入后续结构 QA 的水平。
- `需要调整`：方向成立，但存在可明确局部修复的问题。
- `失败`：命中一眼否决项，停止本案例，不得声明 Skill 通过。

结果与截图证据存放在 `evals` 结果目录，不写入生产项目清单，也不写入客户预览。
